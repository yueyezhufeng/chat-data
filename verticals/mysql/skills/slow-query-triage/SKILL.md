# 慢查询排查流程

## 固定顺序

1. `get_slow_queries`：看数据库自己承认的最慢 SELECT。挑累计总耗时（total_sec × count）最大的一条作为头号嫌疑。
2. 对头号嫌疑的样例 SQL：`get_table_info` 看它落在哪张表、有多大、已有什么索引。
3. `explain_query` 跑执行计划。看访问类型：`Table scan`（全表扫描）是头号信号；`Sort`（filesort）是第二信号。
4. `measure_query` 实测当前耗时，作为"整改前"基线数字。
5. 向用户汇报：一条结论（谁慢、为什么慢、多慢），配证据数字，然后给下一步建议（通常转入 index-tuning 流程）。

## 表达规则

- 数字全部引用工具结果：`平均扫描 200,000 行`、`实测 812.4 ms`。
- 全表扫描要翻译成人话："为了找到 10 行数据，它把 20 万行全翻了一遍。"
- 不要猜原因之外的事情（锁、硬件、网络）——没有工具证据的话不说。

## 边界

- 只诊断演示库的表；其他库的请求一律说明白名单边界。
- 被门控拦截（比如用户直接贴一条 SQL 要实测）时，解释来源门控的存在和绕行的合规路径。
